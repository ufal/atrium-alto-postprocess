## 🎯 Goal & Core Constraint
Refactor the draft JSON-2-TXT extractor introduced in `v1.2.1-beta` so it aligns with the `atrium_document.schema.json` paradata-pair accretion model. It must transition from a raw plain-text output script to a JSON-to-JSON mutation tool. It must ingest `doc.json`, update exactly its owned text structures, preserve all unrelated metadata, and correctly implement the missing `--force-single-page` CLI flag. Additionally, the CLI execution path must be validated via end-to-end (E2E) subprocess testing.

## 🏆 Headline Findings & Conclusions

**1. This was a smaller lift than the original framing suggested — most of the "contract migration" had already happened.**
Auditing `test` HEAD before writing any code turned up that issue #13's earlier work (`atrium_document.py` + `document_hook.py`) had already given `extract_JSON_2_TXT.py` a working Extraction/Accretion split, field-level ownership boundaries (`BLOCK_OWNERS`/`BLOCK_FIELD_OWNERS`), and semantic preservation of untouched blocks. `main()` was already calling `document_hook.write_document_block()` per document after extraction. The "major refactor" the original plan called for turned out to be unnecessary — confirmed via a manual smoke test before touching any code, then left alone. The genuinely missing piece was narrower: the `--force-single-page` flag did not exist in any form, there was no dedicated test coverage for the accretion contract, and there was no E2E subprocess suite.

**2. `--force-single-page` is now a document-assembly policy switch, exactly as planned.**
Implemented as a `force_single_page` parameter on `document_hook.pages_and_content_from_text()`: by default one `pages[]` row is written per source page; with the flag, every source page for a document collapses into a single `pages[]` row (`page: "1"`) whose `ocr.source_pages` records the original page labels in concatenation order — so the source-page mapping is auditable rather than lost. `content.text` is identical either way (always the full document, pages joined in order on a blank line) — the flag never changes what text is extracted, only how the `pages[]` array describes it.

**3. The CLI flag had to be wired through configuration, not just argparse, because of how the pipeline invokes this script.**
`run_pipeline.py` calls `extract_JSON_2_TXT.py` as a bare subprocess with no extra arguments. A CLI-only flag would have been unreachable from orchestrated runs. Resolution: `--force-single-page` is tri-state (`None` when absent) and falls back to a new `[EXTRACT].FORCE_SINGLE_PAGE_JSON` config key when unset, so both direct invocation and pipeline orchestration can opt in.

**4. The "byte-identical" requirement resolved to semantic preservation, matching existing project precedent.**
Rather than introducing a format-preserving JSON library, we kept `atrium_document.py`'s existing behavior (baseline deep-copied, deterministically re-serialized) as the standard, since that's already how every other tool in the pipeline satisfies this same clause. Locked in with a dedicated test (`test_accretion_preserves_unrelated_metadata_and_co_owned_fields`) that builds a baseline `doc.json` with page-classification + nlp-enrich contributions and asserts they survive this extractor's own contribution byte-for-byte at the value level, on both untouched blocks and co-owned `pages[]` fields.

**5. E2E subprocess testing is now real, not aspirational.**
`tests/test_json_subprocess.py` shells out via `subprocess.run([sys.executable, ...])` for every scenario: successful extraction across heterogeneous JSON shapes, the CLI flag, the config-only fallback (mirroring exactly how `run_pipeline.py` invokes it), malformed CLI arguments (exit code 2), a missing input CSV (exit code 1 with a clear message), and corrupted/malformed JSON inputs — both partial failure (mixed good/bad pages, `Success rate: 50.00%`) and total failure (`Success rate: 0.00%`), confirming the script degrades gracefully rather than crashing. Every test runs with `cwd` pointed at a fresh `tmp_path`, never the real repo root, so the script's hardcoded `paradata/` output directory can't pollute the working tree.

**6. Found and fixed an unrelated documentation gap while in the area.**
The json-keys extraction method had zero coverage in `README.md` despite existing in code and being wired into `run_pipeline.py`'s `--method json-keys` option — the other three ALTO-based extraction methods each have a documented subsection, but this one didn't. Added the missing "4th alternative" subsection (Step 3) plus a `doc.json` accretion explainer and a `--force-single-page` behavior table, with a matching Table-of-Contents entry.
