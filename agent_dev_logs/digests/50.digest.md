## 🎯 Goal
The published `atrium-alto-postprocess` image already installs a commit-pinned `alto-tools` at build time. The E2E lane then re-installs it from a moving `master` **inside that image, at run time**. Make the shipped artifact carry a working `alto-tools`, and delete the runtime patch.

## 🔎 Verified state

**The pin exists and is installed.** `setup/requirements.txt:8`:

```
alto-tools @ git+https://github.com/cneud/alto-tools.git@1f4f01e5f6ac3562740e39948442973b9cb94be4
```

with the comment above it (`:5-6`) recording *why* it must come from git rather than PyPI: the released `alto-tools` 0.1.0 wheel has no `-s` statistics flag at all (verified upstream: `alto-tools -s` → "unrecognized arguments: -s"). `Dockerfile:38` installs that file:

```dockerfile
RUN pip install --index-url ${TORCH_INDEX_URL} torch \
    && pip install -r setup/requirements.txt -r service/requirements.txt …
```

**And the E2E lane overrides it.** `atrium-project/.github/workflows/e2e-pipeline-smoke.yml:274`, Stage 2, against the already-published image:

```
--entrypoint /bin/sh … -c "pip install https://github.com/cneud/alto-tools/archive/refs/heads/master.zip && export PATH=\"\$PATH:/home/atrium/.local/bin\" && python run_pipeline.py …"
```

A commit pin, overridden by a moving `refs/heads/master`, in the release artifact, at the moment of testing it. Whatever that lane proves, it is not a property of the published image — which is the whole of factor V.

**Root-cause hypothesis, and it is testable in one command.** The build-time `pip install` runs as **root** — `USER atrium` appears only at `Dockerfile:79`, forty-one lines later — so the `alto-tools` console script lands in `/usr/local/bin`, which is on `PATH` for every user. The runtime patch installs as `atrium` (non-root ⇒ implicit `--user`) into `/home/atrium/.local/bin`, and has to re-export `PATH` to reach it. That is the signature of a workaround written before the build-time install existed, or before it worked. It may be **stale**.

```bash
docker run --rm --entrypoint alto-tools ghcr.io/ufal/atrium-alto-postprocess:<tag> --version
```

That single command decides whether this issue is a two-line deletion in the hub's workflow or a real packaging bug. Run it first.

## 🔎 The two call sites — what "only the used functionality" means

Both shell out to the CLI; neither imports the package:

| Site                        | Call                                                        | Guard                                                                         |
|-----------------------------|-------------------------------------------------------------|-------------------------------------------------------------------------------|
| `extract_ALTO_2_TXT.py:104` | `["alto-tools", "-t", str(xml_path)]` — page text to stdout | `shutil.which("alto-tools")` at `:124`, exits with a CRITICAL ERROR if absent |
| `alto_stats_create.py`      | `alto-tools -s` — statistics                                | —                                                                             |

So the entire dependency surface is **two CLI flags**. That is what makes #53's "copy only the used functionality" preferred over re-pinning: vendoring the `-t` and `-s` code paths removes a `git+` dependency, a `shutil.which` guard, a `PATH` export and the runtime patch in one move, and replaces a subprocess boundary with a function call.

**Attribution is already half-done**, which lowers the cost further: `extract_ALTO_2_TXT.py:161` already seeds `alto_tools` as an "always" paradata component carrying its Apache-2.0 licence. The vendored module needs the licence header and the upstream commit recorded in it; the paradata side already says the right thing.

## ⏳ Open
- **Vendor, or fix the install?** #53 states a preference (vendor). It is the right call if the `--version` probe shows a genuine packaging problem. If the probe shows the image is already fine, the cheapest correct fix is deleting the runtime patch and *keeping* the pin — and vendoring becomes an optional cleanup rather than the fix. **Run the probe before choosing.**
- **The layoutreader clone** (`Dockerfile:42`) is unpinned — `git clone --filter=blob:none --no-checkout --depth 1 …/layoutreader.git`, sparse-checkout `v3`, no commit. Same class as B9, and named in this issue's rider. `--depth 1` means the pin must be added as an explicit fetch of a commit, not just a `--branch` flag.
- **Does the E2E lane even exercise `-s`?** Stage 2 runs `run_pipeline.py` with a config; whether the statistics path (the *only* reason the git pin exists) is on that path is unverified. If it is not, the pin's justification is untested in CI — which is worth knowing before vendoring code to preserve it.
