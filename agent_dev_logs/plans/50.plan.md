# Strategy — Issue #50: stop re-resolving `alto-tools` inside the published image at run time

> Issue [\#50](https://github.com/ufal/atrium-alto-postprocess/issues/50) · Labels: `enhancement`, `development`, `dependencies` · Parent: [atrium-project#53](https://github.com/ufal/atrium-project/issues/53) (factor V) · Split with [atrium-project#62](https://github.com/ufal/atrium-project/issues/62)
> **Status: 🔴 Not started. Closes roadmap B9 — the last live §2.1 breakage. Step one is a one-command probe that determines the whole shape of the fix. Evidence in [`../digests/50.digest.md`](../digests/50.digest.md).**

## Context

This image installs `alto-tools` from a **commit pin** at build time (`setup/requirements.txt:8`, installed by `Dockerfile:38`). The hub's E2E lane then installs it again from a **moving `master`**, inside the already-published image, at run time (`atrium-project/.github/workflows/e2e-pipeline-smoke.yml:274`).

That is factor V stated as plainly as it can be: a release artifact re-resolving its own pinned dependency after release. It is roadmap **B9**, unchanged through three roadmap refreshes, and #53's sweep on 2026-09-09 confirmed it as the last live §2.1 item.

#53's stated preference is to retire the dependency rather than re-pin it: *"just copy the required files and only the used functionality + reference it in docs clearly."* This plan takes that as the direction but gates it behind a probe, because the cheapest correct fix might be smaller.

## Strategic actions

### A — Probe first. It decides everything downstream.

```bash
docker run --rm --entrypoint alto-tools ghcr.io/ufal/atrium-alto-postprocess:<published-tag> --version
docker run --rm --entrypoint sh   ghcr.io/ufal/atrium-alto-postprocess:<published-tag> -c 'command -v alto-tools; alto-tools -s --help 2>&1 | head'
```

Two outcomes, two different issues:

- **The pinned `alto-tools` works in the image** (likely — the build install runs as root, so the console script is in `/usr/local/bin`, and the runtime patch's `--user` install plus `PATH` export is the signature of a stale workaround). Then **B9 is a deletion**: the runtime patch goes, the pin stays, and vendoring becomes an optional follow-up rather than the fix.
- **It does not work** — missing script, wrong `PATH`, or `-s` absent despite the pin. Then there is a real packaging bug, and §B is the answer.

Do not skip this. Vendoring ~two code paths from an upstream project is a reasonable amount of work to take on for a real defect and a poor trade for a stale workaround.

### B — Vendor the two used code paths (if §A shows a real defect, or as the deliberate cleanup)

The entire dependency surface is **two CLI flags**:

- `-t` — page text extraction, `extract_ALTO_2_TXT.py:104`
- `-s` — statistics, `alto_stats_create.py`; the *only* reason the git pin exists, since the released 0.1.0 wheel lacks `-s` (`setup/requirements.txt:5-6`)

Vendor those two paths into a module in this repo, and:

1. **Carry the Apache-2.0 licence header verbatim** and record the upstream commit (`1f4f01e5f6ac3562740e39948442973b9cb94be4`) in the file. The paradata side already claims this attribution (`extract_ALTO_2_TXT.py:161`), so the licence must actually be present in the tree for that claim to be true.
2. **Replace the subprocess calls with function calls** and delete the `shutil.which` guard at `:124` — a guard for a binary that can no longer be absent is misleading, and its CRITICAL ERROR message would become unreachable.
3. **Remove `alto-tools` from `setup/requirements.txt`**, keeping the explanatory comment reworked to say where the code now lives and why.
4. **Reference it in the README** with upstream origin, commit and licence — #53's "reference it in docs clearly", and this issue's fourth acceptance bullet.

Keep the vendored code minimal. Copying the upstream module wholesale re-imports code paths nothing calls, which is the same maintenance burden in a new place.

### C — Pin the layoutreader clone

`Dockerfile:42`:

```dockerfile
RUN git clone --filter=blob:none --no-checkout --depth 1 \
        https://github.com/FreeOCR-AI/layoutreader.git /tmp/layoutreader \
    && git -C /tmp/layoutreader sparse-checkout init --cone \
    && git -C /tmp/layoutreader sparse-checkout set v3 …
```

`--depth 1` on a branch means the build resolves to whatever the tip is that day. Because of the shallow clone, pinning is not a `--branch <sha>` flag: use `git init` + `git fetch --depth 1 origin <sha>` + `git checkout <sha>`, keeping the sparse-checkout of `v3`.

Same class of defect as B9 — an unpinned resolution in a build — and named in this issue's rider.

### D — Sequence with the hub

**#50 lands first, then [atrium-project#62](https://github.com/ufal/atrium-project/issues/62) restructures Stage 2.** That stage fails without a working `alto-tools` in the image, and a red E2E lane blocks merges across all six repos.

The two issues carry duplicate acceptance bullets. Two are #62's (`no --entrypoint override`, `grep -c "pip install"` = 1) and cannot be satisfied from this repo. Do not tick them here. The digest carries the division table.

## Verification / done-criteria

- [ ] The probe in §A is run against a **published** tag and its output recorded on the issue. This is the finding, whatever it says.
- [ ] A freshly built `atrium-alto-postprocess` image extracts text and produces statistics **with no run-time `pip install`** — exercise both paths, not just `-t`.
- [ ] `run_pipeline.py` completes the E2E config path inside the image with no `PATH` export and no `/bin/sh` wrapper.
- [ ] If vendored: the licence header and upstream commit are present in the tree, and the README documents origin + licence. `extract_ALTO_2_TXT.py:161`'s paradata claim matches what is actually in the repo.
- [ ] `Dockerfile:42` resolves to a fixed commit; two builds a week apart produce the same layoutreader tree.
- [ ] The repo's existing test suite passes unchanged — the extraction output must be identical before and after, byte for byte on the fixtures. A vendoring that subtly changes text extraction is a data-quality regression that no CI in this ecosystem would catch.
- [ ] `-s` statistics output is verified explicitly. It is the reason the pin exists and it may not be on the E2E path at all (see Open, below).

## Open questions

- **Is `-s` exercised anywhere in CI?** The git pin exists solely because the PyPI wheel lacks `-s`. If no lane runs the statistics path, that justification has never been tested, and vendoring code to preserve it should come with a test that does.
- **Which fix does the probe select?** Deletion (§A) or vendoring (§B). Recorded here so the choice is made on evidence rather than on the issue's default.

## Out of scope

- **The hub workflow.** [atrium-project#62](https://github.com/ufal/atrium-project/issues/62) owns `e2e-pipeline-smoke.yml`.
- **`flexiconv` pins** in `atrium-nlp-enrich` and `atrium-llm-enrich`. Cited in #62's rider, fixable in neither this repo nor the hub, and currently unowned — flagged in both digests so it is not lost.
