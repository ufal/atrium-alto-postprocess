## Context

Issue #37 addresses a critical integration gap introduced in `v1.2.1-beta`. The draft JSON-2-TXT extractor successfully generalizes plain-text extraction but outputs isolated raw text files. However, the ecosystem (specifically downstream tools like `atrium-llm-enrich`) converged on July 31st around the `atrium_document.schema.json` standard.

The extractor must be refactored to conform to the **paradata-pair accretion model**. This means the script is no longer a simple text dumper; it must accept a `doc.json` file, insert/merge extracted text into designated schema blocks, and output an updated `doc.json` while leaving unrelated metadata untouched. Additionally, a `--force-single-page` flag must be implemented to collapse segmented JSON structures into a single page.

A recent update to the issue mandates the inclusion of **E2E subprocess testing** to simulate real-world CLI execution and ensure stability against argument parsing and environmental constraints.

## Research: Accretion Semantics and State Preservation

We audited the current requirements against the canonical `atrium_document` schema and downstream consumer expectations:

**1. The Accretion Contract:**
The extractor is only authorized to touch specific text blocks. The formula is: `input document + new extraction result = updated document`. Rebuilding the document from scratch is forbidden as it risks dropping unmapped fields.
`[DONE — already satisfied by DocumentRecord/document_hook.write_document_block(); confirmed, not re-implemented.]`

**2. The Byte-Identical Constraint:**
The issue explicitly mandates that "untouched parameters from the input JSON remain byte-identical." Standard Python `json` parsing alters formatting. We must resolve whether this means literal byte-for-byte serialization preservation (requiring a specialized JSON library) or strict semantic preservation (`json.loads(input)["metadata"] == json.loads(output)["metadata"]`).
`[DONE — resolved to semantic preservation, matching the precedent already set project-wide by atrium_document.py (DocumentRecord deep-copies the baseline and re-serializes deterministically with json.dump(..., indent=2)). No format-preserving library introduced; see Risks below.]`

**3. Page Assembly:**
`--force-single-page` needs to be deterministic. If a document has multiple pages or segmented structures, this flag must concatenate the text sequentially without data loss or duplication, outputting exactly one page object within the updated `doc.json`.
`[DONE — implemented in document_hook.pages_and_content_from_text(force_single_page=...); see D4 below.]`

**4. CLI and Environment Testing:**
Unit tests are insufficient for validating the integration points. We must test the `--method json-keys` execution path natively via `subprocess` to catch edge cases in file I/O permissions, argument parsing, and system-level exit codes.
`[DONE — tests/test_json_subprocess.py, 11 tests, all via real subprocess.run().]`

## Algorithm sketch for Accretion

1. Load existing `doc.json`.
2. Locate document/page/text structures defined by `atrium_document.schema.json`.
3. Extract text from the source representation using the decoupled extraction layer.
4. **Assembly check:**
   * If `--force-single-page` is active: concatenate all extracted text into a single page object sequence.
   * If default: map text blocks to their respective page/segment paths.
5. Mutate **only** the owned text blocks in the parsed document tree.
6. Verify preservation invariants for all non-owned fields.
7. Write the resulting updated JSON to disk.

`[Confirmed as-implemented — this is exactly what main()'s existing per-doc loop + document_hook already did before this session; step 4 is the only step that changed.]`

## Risks / open questions

| Risk                                      | Mitigation                                                                                                                                                                                                                                                                                    | Status                                                                                                                                                                                                     |
|-------------------------------------------|-----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| Literal "byte-identical" preservation     | Standard Python `json` module does not preserve bytes (whitespace/key order). If literal byte-for-byte is strictly required, investigate libraries like `ruamel.yaml` (in JSON mode) or `json5`. Otherwise, clarify with stakeholders that "semantic preservation" satisfies the requirement. | **Open** — resolved to semantic preservation for now (consistent with existing `atrium_document.py` behavior project-wide); flag to DanaKriv if the literal-bytes reading is actually required downstream. |
| Accidental data loss during concatenation | Ensure `--force-single-page` has stable newline handling and deterministic ordering so paragraphs don't run together.                                                                                                                                                                         | Closed — `"\n\n".join()` in fixed page-ID order; `ocr.source_pages` makes the concatenation order auditable; covered by `test_pages_and_content_force_single_page_collapses_rows`.                         |
