# [\#50 Issue](https://github.com/ufal/atrium-alto-postprocess/issues/50) `open`: Build, release, run: stop re-resolving alto-tools inside the published image at run time
**Labels**: `enhancement`, `development`, `dependencies`


#### <img src="https://avatars.githubusercontent.com/u/65828620?u=80b39d3cb2967c52e1d4af28dcefc7a1efdfdc79&v=4" width="50">[K4TEL](https://github.com/K4TEL) opened issue at [2026-09-10 12:20](https://github.com/ufal/atrium-alto-postprocess/issues/50):

The clearest possible build/release/run violation: a release artifact that re-resolves its own pinned dependency at run time.

`.github/workflows/e2e-pipeline-smoke.yml:274`, inside Stage 2, running **against the already-published image**:

```
--entrypoint /bin/sh
ghcr.io/ufal/atrium-alto-postprocess:<tag>
-c "pip install https://github.com/cneud/alto-tools/archive/refs/heads/master.zip && export PATH=… && python run_pipeline.py …"
```

`atrium-alto-postprocess/setup/requirements.txt:8` pins `alto-tools @ git+https://github.com/cneud/alto-tools.git@1f4f01e5f6ac3562740e39948442973b9cb94be4`, and `Dockerfile:38` installs that file at build time. So the E2E lane does not merely duplicate the build — it **overrides a commit pin with a moving `refs/heads/master`**, in the artifact we ship, at the moment we test it. Whatever that lane proves, it is not a property of the published image.

Worth root-causing before deleting: the build-time install runs as root (`USER atrium` only at `Dockerfile:79`), so the console script lands in `/usr/local/bin`, while the runtime patch installs `--user` into `/home/atrium/.local/bin` and re-exports `PATH` to reach it. The workaround may simply be stale. **Step one is `docker run --entrypoint alto-tools ghcr.io/ufal/atrium-alto-postprocess:<tag> --version` against a published tag** — the answer decides whether this is a two-line deletion or a real packaging bug.

### Preferred resolution (per #53, 2026-09-09)

Retire the external dependency rather than re-pin it: **copy in the required files and only the used functionality, and reference it clearly in the docs.** Two call sites, both shelling out to the CLI:

- `extract_ALTO_2_TXT.py:104` — `["alto-tools", "-t", <xml>]` (text extraction), guarded by `shutil.which("alto-tools")` at `:124`
- `alto_stats_create.py` — `alto-tools -s` (statistics; the reason the git pin exists at all, since the released 0.1.0 wheel has no `-s`, per `setup/requirements.txt:5-6`)

Vendoring both paths removes a `git+` dependency, a `shutil.which` guard, a PATH export and the runtime patch in one move. Attribution is already half-handled — `extract_ALTO_2_TXT.py:161` seeds `alto_tools` as an "always" paradata component with its Apache-2.0 licence — so carry the licence header into the vendored module and record the upstream commit in it.

## Rider: close the remaining unpinned refs (factor II)

Factor II is otherwise green (B1 closed — `uvicorn` in all five `service/requirements.txt`). Three unpinned resolutions remain, same class of problem:
- `atrium-alto-postprocess/Dockerfile:42` — `git clone --depth 1 FreeOCR-AI/layoutreader`, no commit

### Acceptance

- E2E Stage 2 runs with **no `pip install`** in its command and **no `--entrypoint` override**, and passes.
- `grep -c "pip install" .github/workflows/e2e-pipeline-smoke.yml` returns 1 (the `tools/e2e/requirements.txt` line at `:102`, which runs on the runner, not in the image).
