Following up on the planning digest above: issue #31 is now implemented, not just designed.

**What changed**
- `page_split.py` — added `split_json_document()` (Family A: nested pages array / Family B: flat tagged list / Family C: single-page fallback), dispatched by extension in `main()` alongside the untouched `split_alto_xml()`. Detection whitelists (`PAGE_LIST_KEYS`, `PAGE_NUMBER_FIELD_KEYS`) match the plan verbatim.

- `setup/config.txt` — added `PAGE_JSON_DIR = data_samples/PAGE_JSON`.
- `README.md` — Step 1 section now documents both ALTO and JSON splitting paths.

**Tests**

- Added `test_page_split.py` coverage for Family A (with/without page-number field, one-level nesting), Family B (triggered + non-triggered), Family C fallback, empty-list edge case, and malformed-JSON handling.
- Updated `test_json_stats_create.py` for filename-derived page numbers.
- `pytest -m "not slow"`: 41/41 passing. `ruff` clean relative to the pre-existing baseline (no new lint introduced).

**Still open / deferred (per the plan)**

- `--force-single-page` escape hatch was deferred out of this pass, not blocking.

- **#31 (alto-postprocess)** is about **ingest**: teaching the pipeline to accept arbitrary OCR-engine JSON as *input* and normalize it to plain text, alongside ALTO XML.
- **https://github.com/ufal/atrium-llm-enrich/issues/13** is about the **output/knowledge-representation contract**: which format(s) downstream tools (translator, nlp-enrich, llm-enrich) coexist on — landing on a three-plane model (annotated Markdown = LLM diet, TEITOK.XML = spatial truth, JSON = canonical search record).

### Where they *should* connect but currently don't:

- `atrium_document.py` (landed in the hub, vendored + trialed in llm-enrich, 13/13 tests passing when I ran them) already hard-codes **block ownership for alto-postprocess** — `content`, `pages` (`quality_score`, `quality_band`, `needs_ocr`, `ocr`, `canvas`), `lines` (`categ`, `quality_score`, `lang`, `text`). That's alto-postprocess's *actual* extracted text and quality metadata being assigned a home in the shared accretion record.
- I grepped the `test` HEAD of atrium-alto-postprocess for any trace of this (`atrium_document`, `DocumentRecord`, `--document-json`, "paradata pair") — **zero hits**. #31's own plan doesn't mention it either. Right now #31 is building a second, disconnected text-output path (files + CSV) while the sibling repo has already shipped a contract expecting alto-postprocess to write into the shared `doc.json` instead.
- Concretely: the https://github.com/ufal/atrium-llm-enrich/issues/13 review thread has an open maintainer TODO from motyc — *"rename/normalise alto-postprocess `program` names (`alto-postprocess` vs `langID-classify` vs `langID-aggregate`)"* — which exists only in llm-enrich's dev logs. I checked: `run_pipeline.py` still stamps every stage's `ParadataLogger` with the same `program="alto-postprocess"` regardless of which script actually ran. That TODO is real, outstanding, and invisible from inside the alto-postprocess repo itself.
- Also worth flagging: https://github.com/ufal/atrium-llm-enrich/issues/13 's own architecture ranks plain TXT as **fallback tier**, below MD and TEITOK, with "unify nlp-enrich onto MD input" as an open item. So while #31 generalizes the TXT-producing path to more input formats, the consuming repo's stated direction is to move *off* TXT as the primary diet. Not wasted work — TXT stays a legitimate fallback — but the two efforts are pulling in slightly different directions on the same data flow, and that hasn't been reconciled anywhere yet.
